# Runbook ترقية قاعدة البيانات — 1.0.7

## النطاق المدعوم

الحد الأدنى المعلن والمدعوم لقاعدة موجودة هو migration `014`. تُرفض قواعد أقدم من ذلك برسالة واضحة؛ أما قاعدة جديدة غير مهيأة فتسلك مسار التهيئة الكامل. أحدث migration منشور في هذا الإصدار هو `065` (توافق التطبيق `1.0.7`، بيانات وصفية فقط)؛ لا يُطبَّق أي ترحيل على الإنتاج ضمن مهمة 1.0.7 إلا عبر `MigrationRunner` بعد النسخة الاحتياطية.

## المسار الآمن من شاشة الدخول

1. تتحقق الشاشة من الاتصال وإصدار القاعدة قبل تسجيل الدخول.
2. على قاعدة `014` أو أحدث، يقرأ Desktop login `must_change_password` فقط إذا كان العمود موجودًا؛ قبل `015` يستخدم قيمة fallback آمنة ولا يخفف شروط الحساب أو الدور.
3. إذا كانت هناك ترقية، يجب أن يكون المستخدم مديرًا فعّالًا.
4. تعرض الشاشة مسار النسخة المقترح تحت مجلد النسخ وتطلب تأكيدًا.
5. يُنفذ `pg_dump` بصيغة custom، ثم يُفحص وجود الملف وحجمه وتُختبر قابليته للقراءة عبر `pg_restore --list`.
6. عند فشل الإنشاء أو الفحص تتوقف العملية قبل فتح أي migration. لا يوجد تجاوز صامت.
7. بعد نجاح النسخة فقط يُشغّل `MigrationRunner`، ويُعرض اسم ملف النسخة في سجل الترقية.

## مصدر الحقيقة والمصالحة

`system.schema_migrations` هو مصدر الحقيقة لتطبيق SQL. بعد نجاح `COMMIT` لا يُحوّل فشل كتابة `system.database_migration_history` إلى ادعاء بأن SQL تراجع. يُبلغ الخطأ باعتباره `MigrationHistoryPendingException`، وفي التشغيل التالي تُعاد كتابة حالة `SUCCESS` بصورة idempotent من سجل `schema_migrations` دون إعادة تنفيذ SQL. يوجد seam اختباري يحاكي فشل الكتابة بعد commit.

## الاسترجاع والـ rollback

إذا فشل SQL داخل transaction فالتراجع يتم داخل PostgreSQL ويُسجل `FAILED`. إذا نجح schema migration فلا يكفي إعادة ملفات التطبيق أو إعادة تشغيل migration؛ استعادة المخطط تتطلب استعادة نسخة قاعدة البيانات. يجب الاحتفاظ بالنسخة الاحتياطية القابلة للقراءة، وتحديد نافذة توقف الخدمة، ثم استخدام مسار `RestoreFileToLocalAsync` للاختبار المحلي أو إجراء استعادة PostgreSQL معتمد للإنتاج.

## التحقق قبل الإنتاج

- نفّذ اختبار clone من `014` إلى آخر migration منشور في بيئة PostgreSQL مؤقتة.
- نفّذ اختبار `065` إلى `065` وتأكد من عدم تغير الجداول أو البيانات.
- نفّذ fault injection لفشل history بعد commit وتأكد من نجاح المصالحة دون إعادة SQL.
- لا تُنفذ ترقية إنتاجية قبل موافقة مدير النظام ونجاح backup قابل للقراءة.

## بيانات اعتماد TASK-06 قبل وبعد القطع

تبدأ نافذة القطع باختبار اتصال حساب 1.0.6 القديم وسلامة النسخة الاحتياطية دون سحب الحساب. بعد إنشاء حسابات 1.0.7 المنفصلة، تُسجل نتائج الاختبارات التالية قبل تبديل الخدمة:

- Dashboard: قراءة التقرير ناجحة، وINSERT/UPDATE/DELETE على الجداول الأساسية مرفوضة.
- Update writer: الكتابة إلى `updates` ناجحة، والوصول إلى `core` و`audit` مرفوض.
- Desktop runtime: دورة مذكرة يومية ناجحة، وUPDATE/DELETE على `audit.logs` مرفوض.
- Migrator: تطبيق migration تجريبي في قاعدة قبول فقط، دون `SUPERUSER` أو `CREATEDB` أو `CREATEROLE`.
- Backup operator: إنشاء نسخة custom وفحصها عبر `pg_restore --list`؛ الاستعادة تُجرى بحساب صيانة منفصل.

بعد نجاح الاختبارات ومراجعة صلاحيات الحسابات، يُبدّل كل عميل إلى السر الجديد، ثم تُراقب الصحة والسجلات. لا يُسحب حساب 1.0.6 قبل إغلاق نافذة التحقق وخروج آخر عميل 1.0.6، وتُسجل عملية السحب ووسيلة الاسترجاع الطارئ.
